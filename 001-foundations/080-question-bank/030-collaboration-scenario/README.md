# 030 문제 세트 (Question Set, QS) — 협업 와 시나리오 (Collaboration & Scenario, CS) (Q021–Q030)

## Q021
재현 가능한 버그를 담당자에게 배정하고 상태를 추적하려고 한다. 가장 적합한 기능은?

A. Issue  
B. Discussion  
C. Star  
D. Gist

<details><summary>정답 및 해설</summary>

**정답: A** — Issue는 버그·기능·작업 추적에 적합하고 Assignee, Label, Milestone 등을 연결할 수 있습니다.
</details>

## Q022
다음 버전의 방향에 대해 폭넓은 커뮤니티 의견을 수집하려 한다. 가장 적합한 기능은?

A. Discussion  
B. Commit  
C. Release  
D. Branch

<details><summary>정답 및 해설</summary>

**정답: A** — Discussion은 Q&A, 아이디어, 공개 토론과 같은 대화 중심 활동에 적합합니다.
</details>

## Q023
Pull Request의 핵심 목적은?

A. Git 설치  
B. 변경을 제안하고 Review·논의 후 병합할 수 있게 하는 것  
C. 계정 2FA 설정  
D. Repository 삭제

<details><summary>정답 및 해설</summary>

**정답: B**
</details>

## Q024
Pull Request에서 수정이 반드시 필요하다고 판단한 Reviewer가 선택할 결과는?

A. Approve  
B. Request changes  
C. Star  
D. Watch

<details><summary>정답 및 해설</summary>

**정답: B** — 필수 수정이 필요할 때 변경 요청을 남깁니다.
</details>

## Q025
Issue의 실제 구현 책임자를 지정하는 데 가장 직접적인 기능은?

A. Assignee  
B. Star  
C. Fork  
D. Sponsor

<details><summary>정답 및 해설</summary>

**정답: A**
</details>

## Q026
여러 Issue를 하나의 릴리스 목표나 기간에 묶어 진행 상황을 추적할 때 유용한 기능은?

A. Milestone  
B. Gist  
C. Codespace  
D. Fork

<details><summary>정답 및 해설</summary>

**정답: A**
</details>

## Q027
아직 작업 중이어서 정식 Review 준비가 되지 않았지만 진행 상황을 공유하고 싶다. 가장 적절한 것은?

A. Draft Pull Request  
B. Repository 삭제  
C. Release 생성  
D. 계정 잠금

<details><summary>정답 및 해설</summary>

**정답: A** — Draft PR은 작업 중 변경을 조기에 공유하고 피드백을 받을 때 유용합니다.
</details>

## Q028
일반적인 GitHub Flow 순서로 가장 자연스러운 것은?

A. Merge → Branch → Issue → Commit → PR  
B. Issue → Branch → Commit → Push → Pull Request → Review → Merge  
C. Review → Issue → Merge → Commit  
D. Pull Request → Issue → Branch → Merge

<details><summary>정답 및 해설</summary>

**정답: B** — 실제 팀 규칙에 따라 변형될 수 있지만 학습 기준 흐름으로 가장 적절합니다.
</details>

## Q029
PR에 자동 Test가 실패한 상태다. 가장 적절한 행동은?

A. 실패 원인을 무시하고 즉시 Merge  
B. Check 결과와 로그를 확인하고 원인을 수정한 뒤 다시 검증  
C. Repository를 Public으로 변경  
D. 모든 Branch를 삭제

<details><summary>정답 및 해설</summary>

**정답: B** — 자동 Check는 변경 품질을 검증하기 위한 신호이므로 원인을 해결하는 것이 우선입니다.
</details>

## Q030
팀이 `main`을 안정적으로 유지하면서 문서 기능을 개발하고 동료 Review 후 반영하려 한다. 가장 적절한 전략은?

A. `main`에서 직접 수정하고 즉시 Push  
B. 작업 Branch 생성 → Commit/Push → PR → Review → Merge  
C. Repository를 Fork 후 삭제  
D. Discussion만 작성하고 코드 변경 없이 종료

<details><summary>정답 및 해설</summary>

**정답: B** — Branch와 PR 중심 흐름은 변경을 분리하고 Review를 거쳐 기본 Branch에 통합하도록 돕습니다.
</details>
