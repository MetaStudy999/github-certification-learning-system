# QBank 010 — Security Suites / Ecosystem

## Q001–Q010

**Q001.** 코드 취약점 분석에 가장 직접적인 GitHub Security 영역은?  
A. Secret Protection  B. Code Security  C. Projects  D. Discussions

**Q002.** 자격증명 노출을 개발 흐름 초기에 예방하는 기능은?  
A. Push Protection  B. Dependency Graph  C. Security Campaign  D. SARIF

**Q003.** 의존성 관계를 파악하는 기본 기능은?  
A. Dependency Graph  B. CodeQL  C. Ruleset  D. Audit Log

**Q004.** 여러 Repository의 보안 상태를 조망하는 데 가장 적합한 기능은?  
A. Security Overview  B. README  C. Codespaces  D. Wiki

**Q005.** 특정 위험 집합을 기간과 책임자 기준으로 줄이기 위한 기능은?  
A. Security Campaign  B. Release  C. Fork  D. Milestone

**Q006.** Prevention-first 전략의 핵심 목적은?  
A. 문제를 가능한 이른 단계에서 막기  B. 모든 Alert 무시  C. Merge 후에만 검사  D. 보안팀만 책임지기

**Q007.** Alert Dismissal에 가장 중요한 운영 원칙은?  
A. 근거와 책임을 기록  B. 모두 자동 닫기  C. 심각도 삭제  D. 로그 제거

**Q008.** Secure SDLC에서 개발자·보안팀·관리자 관계를 가장 잘 설명한 것은?  
A. 역할별 책임을 나누되 협업  B. 관리자만 책임  C. 개발자만 책임  D. 외부 감사자만 책임

**Q009.** Secret Protection과 Code Security의 핵심 차이는?  
A. 자격증명 노출 vs 코드 취약점  B. 둘은 동일  C. 저장소 생성 vs 삭제  D. Issue vs PR

**Q010.** GitHub Security 기능 학습에서 가장 적절한 접근은?  
A. Risk → Feature → Response를 연결  B. 메뉴 이름만 암기  C. 실제 Secret 사용  D. 모든 경고를 우회

## Answers

| Q | 정답 | 핵심 이유 |
|---:|:---:|---|
| 001 | B | Code Security는 코드 취약점 분석 영역입니다. |
| 002 | A | Push Protection은 노출을 사전에 막는 예방형 통제입니다. |
| 003 | A | Dependency Graph가 의존성 관계를 보여 줍니다. |
| 004 | A | Security Overview는 다수 저장소 보안 상태를 집계합니다. |
| 005 | A | Campaign은 목표형 Remediation을 조직화합니다. |
| 006 | A | 예방형 전략은 위험 유입 전 차단에 초점을 둡니다. |
| 007 | A | Dismissal은 근거·권한·감사 가능성이 필요합니다. |
| 008 | A | Secure SDLC는 역할 간 공동 책임 모델입니다. |
| 009 | A | 두 제품 영역의 탐지 대상이 다릅니다. |
| 010 | A | 시험은 기능과 위험·대응의 연결을 요구합니다. |
